2 创建个人仓库

在new Repositories后

在本地仓库目录下

git remote -v

发现为空，即当前仓库没有和任何远程仓库产生联系，所以要先进行remote配置

git remote add github(远程端名称，以后用这个名字代替远程仓库) git@github.xxx/xxxxxx.git(采用ssh协议，去新的建的仓库中复制这个链接) git remote add github git@github.com:xxx/xxxxxr.git

在添加完后，再git remote -v，可以看到了两个远端push fetech一个用于上传一个用于下载

git push github(远端仓库代指名) –all(push所有当前分支)

注意如果远端的一些文件，本地没有(比如创建工程时的readme .gitignore license)，在push的时候会报错，git会提示你先fetch把这些文件先下载 (远端分支和本地分支同名会出现这种情况)

git pull (先fetch远端，将同名分支merge)

git fetch github(远端仓库) main(指定fetch的分支)

fetch后的分支和远端的分支是两个无关联的分支

本地依旧是一个分支

git bracnch -va #将远端的分支也一并打印出来

尝试将两颗树merge

**git merge –allow-unrelated-histories(合并无父子关系的两颗树) github/main(**远端分支名)

在我们做完新文件的add和commit后可以看到两颗树合并了

此时再git push github(远端仓库代指名):master(远程分支名)

git push <远程主机名> <本地分支名>:<远程分支名>

git push <远程主机名> <本地分支名> # 如果本地分支名与远程分支名相同，则可以省略冒号：

我们创建出的github主分支名为main，而本地的主分支名默认为master

https://blog.csdn.net/qq_27525611/article/details/111657348

修改默认分支为master，接下来就能将在页面的分支中将main删除，只留下master

让本地的git同步成和远程分支一个状态

git remote prune github(远程仓库名) # 同步后如果分支在远程被删除则本地也会同步

(删除本地分支 git branch -D 本地分支名)

3 不同人修改了不同文件

两个人维护同一个分支，两个人修改了同分支中不一样的文件

创建新分支的操作的可视化界面在github上现在操作不了，还是需要

** git checkout -b 新分支名 git checkout 新分支名 # 切换到新分支**

git push 远程仓库名 本地分支名 # 将新分支push到github上

git clone 仓库ssh地址 新的仓库名 # 克隆到本地可以重命名仓库

对于远端的新分支，本地没有则操作为

git fatch 远端仓库名 远端分支名 # 先将分支克隆到本地 本地会新增红色名字的远端仓库

**git checkout -b 远端分支在本地的名字 远端分支名 # 根据克隆的远端分支，创建对应的本地分支 **

对于克隆的这个分支做修改，git add，git commit后就可以做git push

如果在我们修改分支的这段时间内有其他用户也修改了分支，并将更新给push了，则此时远端的一些更新，本地是没有的。则我们在本地没有同步远端更新的情况下push是会失败的。 此时需要

git fetch 远端仓库名 远端分支名 # 更新本地保存的远端分支记录

此时的本地分支

有一个commit我们还没有push到远端即ahead 1 ，同时有远端的一个更新我们还没有同步到本地(就是我们之前 fetch出现的新变更)即behind 1。

在本地分支下

git merge 远端分支名(本地远端分支名 红色的那个名字)

将远端更新同步到本地仓库中(绿色)，总的流程是 远端github –fetch–本地远端(红色)–chekout -b or merge同步更新到本地分支(绿色)

接下来再git push就很顺利不会出错

4 不同人修改了相同文件的不同区域

每次修改前先将远端分支pull下来是个好习惯，保证本地分支是最新的更新

**git pull <远程主机名> <远程分支名>:<本地分支名> # git pull 命令用于从远程获取代码并合并本地的版本。**如果远程分支是与当前git所处分支合并，则冒号后面的部分可以省略。

git pull 其实就是 git fetch 和 git merge FETCH_HEAD 的简写。

修改了相同文件的不同区域，并都add和commit了。其中一方先push更新上去了

另一方普通push时就会出错

此时要与3做一样的操作,在pull一次，或者fetch(更新本地远端)+merge(根据本地远端更新本地)

git pull 远程仓库名 远程分支名

此时打开我们共同更新的文件可以看到，别人的更新和自己的更新都保留下来了。

此时再push就是ok的

当发生冲突后git会提示发生冲突的文件是哪个

去看到那个文件，可以看到文件中会标出发生冲突的位置

Head

====

发生冲突位置的远端文件内容

本地远端仓库哈希

接下来就需要两个开发者交流，来决定需要保留哪些内容。

在本地完成解决冲突后使用 git commit提交冲突修复，再push更新到远端。

或者我们选择撤销这个产生错误的merge操作，恢复到merge之前的状态

6 如何处理同时变更了文件名和文件内容

有人先变更了文件名并先push了其他人不知道。

其他人还是在原来的文件名下对文件做修改，后也想push,发现报错。

则尝试git pull 同步远端更新到本地。没有报错！！git能够检查到是远端和本地文件名的不同导致的错误。并更新本地文件名，保留本地文件修改。

8 git使用禁忌

  1. 禁止向远程集成分支执行git push -f强制更新远程的操作

我们本地在push的时候，假如我们不是fast forward的(本地版本新于远端版本)，是会报push失败。我们需要做pull操作先将本地的内容和远端做更新同步。

假如在push失败的情况下强制push -f，将远端内容强制变为和本地一样。并且强制push某个commit将会导致远端之前记录的在这个commit之后的记录全部都没了。

  1. 禁止pull公共分支到本地，做rebase操作(改变历史)。(公共分支的历史只能往前走，不能回到过去的状态)

做变更要基于现在最新的commit,在往上增加的方式来调整。**而不要对公共分支上的过去commit做rebase变更,**因为这些commit可能被其他人pull到本地做新的开发，如果我对这些commit做rebase修改即将会导致其他人跟远程仓库不再是fast forward的，又要做merge。

13挑选合适的分支集成策略

insight-nwtwork可以看到仓库版本树的演进过程(commit)，setting-general-pull request中有原来的merge button选项，

主干开发使用allow rebase merging。

在pull requests栏选择new pull request,将beijing分支merge到master分支中

经过自动化检查通过后，出现我们允许的merge方式，挑选一个进行merge

  1. create a merge commit

beijing分支的所有commit会被加到master分支中，以一个新的commit的形式存在

原分支树

merge后分支树，master分支中多了一个commit，**集合beijing分支在与master公共分支后的所有commit(3个)**的commit。

merge后beijing分支其实就没有存在的意义了，github会提示你是否要删掉beijing分支。merge后beijing分支的指针就是指向最新的这个master commit

  1. squash and merge

将beijing分支的所有commit合成一个commit，然后和到master分支中

merge后，beijing分支依旧有其存在的必要，master分支中多了一个**集合beijing分支在与master公共分支后的所有commit(3个)**的commit。

  1. rebase and merge

不动被merge的分支beijing，将beijing分支的commit一一地按照顺序加入到master分支中
