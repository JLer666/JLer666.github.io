unique_lock – 互斥锁（mutex）的封装类 互斥锁mutex 互斥：在任意时刻只能有一个线程持有互斥锁并访问共享资源。当一个线程已经获得了互斥锁，其他线程对该互斥锁的请求将会被阻塞，直到持有互斥锁的线程将其释放。 可重入性：同一个线程可以多次获取同一个互斥锁而不会导致死锁（deadlock），也就是说，互斥锁可以被递归地加锁和解锁。 公平性：互斥锁通常采用先到先得的策略来分配锁的使用权，**即等待时间最长的线程优先获得锁的使用权，**这样可以避免饥饿（starvation）情况的发生。 死锁风险：如果不正确地使用互斥锁，就可能会出现死锁的情况。例如，当一个线程在持有一个互斥锁的同时试图获取另一个互斥锁，而另一个线程正好持有这个互斥锁，那么两个线程都无法继续执行下去，从而导致死锁。 性能开销：由于互斥锁需要进行加锁和解锁操作，所以会带来一定的性能开销，尤其是在高并发的场景中。因此，在编写代码时应该尽可能地减少锁的使用，并且保证锁的作用范围尽可能小，以提高程序的并发性能。 std::recursive_mutex – 可重入互斥锁（recursive mutex） 继承自std::mutex，并添加了可重入性（即同一个线程可以多次获取该锁 – mutex中说的可递归地加锁和解锁）的支持。与普通的互斥锁不同，当一个线程多次尝试获取std::recursive_mutex时，只有第一次获得锁才会阻塞，后面的请求会累积在该线程上，并通过解锁操作来依次释放锁。 使用std::recursive_mutex可以避免死锁和其他竞争条件（race condition）的出现，尤其是在递归调用的情况下非常有用。例如，在一个递归函数中，可能需要多次获取同一个锁来保护共享资源。如果使用普通的互斥锁，则在递归过程中可能会出现死锁的情况，因为线程在持有锁的同时又试图获取同一个锁。而使用std::recursive_mutex则可以避免这种情况的发生，从而提高程序的鲁棒性和可靠性。 与std::mutex类似，std::recursive_mutex也提供了lock()、unlock()等方法来控制锁的获取和释放，以及try_lock()方法来尝试获取锁。此外，std::recursive_mutex还支持std::lock_guard和std::unique_lock等RAII（资源获取即初始化）类型的封装，使得锁的管理更加方便和安全。 需要注意的是，由于std::recursive_mutex支持递归调用，所以在使用时应该确保每次加锁和解锁成对出现，否则可能会导致严重的竞态条件和内存泄漏等问题。 std::unique_lockstd::recursive_mutex lock(mutex_); 锁局部变量在函数结束后自动释放 宏单例 #define DECLARE_SINGLETON(classname) \ public: \ static classname *Instance() { \ static std::atomic<classname*> instance = { nullptr }; \ if (!instance) { \ static std::once_flag flag; \ std::call_once(flag, \ [&] { instance.store(new (std::nothrow) classname()); }); \ } \ return instance.load(); \ } \ private: \ classname(); \ classname(const classname &) = delete; \ classname &operator=(const classname &) = delete; std::async与furture对象 ...
