执行模型是CUDA对硬件再高一层的抽象。执行模型提供一个操作视图，说明如何在特定的计算架构上执行指令。GPU架构是围绕流式多处理器(SM–CUDA1中有提到)的可扩展阵列搭建的，可以复制这种架构的构建块来实现GPU的硬件并行。

上图为Fermi SM图，组件包含core(CUDA核心)，Shared Memory/L1 Cache共享内存/一级缓存,Register File寄存器文件,加载/存储单元 LD/ST,特殊功能单元SFU,线程束调度器Warp Scheduler

GPU含多SM(GPU硬件的计算单元的单位是SM数量)，每个SM都能支持数百个线程并发执行。所以在同个GPU上并发数千线程是可能的，当启动一个grid时，block被分布在可用的SM上执行。

注意: 当一个blcok被分配给一个SM后，他就只能在这个SM上执行了，不可能重新分配到其他SM上了，多个block可以被分配到同一个SM上 。

同一线程内，指令利用指令级并行将单个线程处理成流水线。CUDA采用单指令多线程(SIMT)架构管理和执行线程，每32个线程(这里强调一下不同设备的warp线程数是不同的，但到目前基本上所有warp线程数量都是32)为一组被称为线程束(warp)，线程束中的所有线程同时执行相同的指令 ，每个线程都有自己的指令地址计数器和寄存器状态，利用自身数据来执行对应的指令。每个SM都将为属于它的block上的线程划分到不同的warp，同个warp中的线程一定来源于同个block，然后在硬件上调度执行，在某时刻T，SM上只执行一个warp，一旦warp被调度到片上那么其在结束之前不会离开SM 。所以block的不同线程可能会以不同的速度前进**，block内的不同线程进度都不一样，但是同个warp的线程有相同的进度**。

SIMT与SIMD(单指令多数据)机构类似。都是将相同指令广播给多个执行单元来实现并行，关键的区别是SIMD要求同个向量中的所有元素要在一个统一的同步组中执行，而SIMT允许属于同一warp的多个线程独立执行。尽管warp中的所有线程在相同的程序地址上同时开始执行，但是因为判断分支的存在(不同的线程执行不同的逻辑分支)不同的线程的行为可能不同。由于SIMT允许warp中的多个线程独立执行，这将为并行编程带来更多变化，同个核函数内可为线程分配不同行为，并行处理线程、标量线程、协调线程的代码可写在同一个核函数内。

SIMT模型包含SIMD所不具备的特征：

每个线程都有自己的指令地址计数器

每个线程都有自己的寄存器状态

每个线程都可以有一个独立的代码执行路径

在很多的cuda c代码中，会出现很多与32相关的数字16、64、128…，从概念上说32是SM用SIMD方式执行并行任务的工作粒度，优化工作负载(数据划分)以适应线程束的边界，这样能更有效地利用GPU计算资源。

在SM中共享内存和寄存器是非常重要的资源，共享内存被分配在SM上的常驻block中，寄存器在线程中被分配，block中的线程通过这些资源进行合作和通信，CUDA将这些资源分配到SM上的所有常驻线程，所以这些资源也限制了SM上活跃的warp数量，活跃的warp数量对应于SM上的并行量。block中的warp会以任意顺序被调度，但活跃的warp数量会由SM的资源限制，当warp由于一些原因限制时(等待同步，或等待读取设备内存值，SM会从同一SM上的常驻block中调度其他可用的warp，在并发(属于同个block执行同个核函数)的warp间切换没有开销，因为硬件资源已经被分配给SM上的所有线程和block中，所以那个新被调度的warp状态已经被存储在SM上。

Fermi架构#

fermi是第一个完整的GPU架构，采用512个CUDA core，每个core都有一个全流水线的整数算术逻辑单元(ALU)和一个浮点运算单元(FPU)，在每个时钟周期执行一个整数或浮点指令。core被分配到16个SM中，每个SM有32个core。Fermi架构有6个384为的GDDR5 DRAM存储器结构支持6GB的全局内存(global memory)，通过PCIe总线与CPU相连，GigaThread引擎是一个全局调度器，用来将block分配到SM的warp调度器上。16个SM共享一个耦合的768kb的L2 cache。

每个SM有16个加载/存储单元 LD/ST，允许每个时钟周期内有16个线程(warp内线程数量的一般)计算src和target地址，特殊单元SFU执行固有指令如正弦、余弦、平方根和插值，每个SFU在每个时钟周期内的每个线程上执行一个固有指令。

每个SM有2个warp调度器和2个指令调度单元。当一个block被指定给一个SM时，block中的所有线程被分成warp，两个warp调度器选择其中两个warp，再用两个指令调度器存储两个warp要执行的指令，将一个指令发送到一个组上并行执行(调度执行顺序如下图)，组里有16个core、16个加载/存储单元 LD/ST或4个SFU特殊功能单元。Fermi架构计算性能2.x，可以在每个SM上同时处理48个warp,即一个SM上同时常驻1536个线程。

Fermi架构的关键特征是有一个64kb的片内可配置存储器，被分配给共享内存或l1 cache。共享内存对性能影响非常关键，共享内存允许一个block上的线程相互合作，高效通信。当CUDA执行API时，可通过配置此存储器来调整共享内存和l1 cache大小，通过配置内核函数的片内存储器配置来提高性能。

Fermi架构也支持多内核函数并发，同时启动多个内核，并发执行内核允许执行一些小的内核程序来充分利用GPU，如下图右侧所示

Kepler架构#

下图为Kepler K20X芯片框图，含15个SM和6个64位内存控制器。

K20X的关键创新是SM结构的创新，新的SMX单元包含,192个单精度core,64个双进度core，32个SFU以及32个LD/ST如下图所示。每个SMX包含4个warp调度器和8个指令调度器，在单一SMX上同时发送和执行4个warp。K20X(计算能力3.5)可以同时在每个SMX上调度64个warp，即在一个SMX上可同时常驻2048个线程。K20X中的寄存器文件容量达64kb是Fermi的两倍。同时K20X还允许片内存储器在共享内存和L1 cache间有更多分区。K20X可提供超1TFlop的峰值双精度计算能力，相较于Fermi功效提高80%，每瓦性能提升3倍。

动态并行也是K20X的新特性，它允许GPU动态启动新的grid，有了这个新特性后任一内核都能启动其他内核，这将更容易创建和优化设备端递归。因为这个新特性的存在，GPU能够嵌套启动内核，消除了与CPU通信的开销大大提升了设备端运行效率如下图左侧所示。

Hyper-Q增加了更多的CPU与GPU间的同步硬件连接，确保CPU能在GPU执行的同时运行更多任务，使用K20X是既能增加GPU利用率也能减少CPU闲置时间。Fermi依赖单一硬件队列来实现从CPU到GPU间传送任务，这将导致一个单独任务就能阻塞该任务后的所有其他任务。Hyper-Q消除这个限制，K20X在主机与GPU间提供了32个硬件工作对了，提高GPU的利用率。

Profile-Driven Optimization#

在测试中我们需要监控程序并进行性能分析，包含 程序的时间/空间复杂度，特殊指令的使用，函数调用的频率和耗时。CUDA会将SM的计算资源在改SM中的多个常驻block之间进行分配，这种分配导致一些资源称为性能限制，性能分析工具能帮助我们理解计算资源是如何利用的。

CUDA提供两个性能分析工具nvvp独立的可视化分析器显示CPU与GPU上的程序活动时间表，nvvp可作为一个独立的应用启动也可作为Nsight Eclipse Edition的一部分 和nvprof命令行分析器 获取CPU与GPU上CUDA关联活动时间表，包括内核执行、内存传输和CUDA API调用，也可以获取硬件计数器和CUDA内核的性能指标。

在CUDA性能分析中，事件是可被计算的 它对应于一个内核的执行期间的总的硬件计数器(hardware

counter)。 指标是内核的特征，它由一个或多个事件计算得到。 大多数计数器的来源是流式多处理器而非整个GPU。 单次运行只能获得几个计数器，有些计数器互相排斥，多个性能指标分析往往需要所有相关的计数器。

由于block和warp调度顺序的变化，重复运行获得的计数器值可能不完全相同。

warp and block#

warp是SM中最基本的执行单元，当一个grid被启动后，grid中的block分布在SM中，档一个block被调度到一个SM上，block中的线程会被进一步划分为warp。一个warp一般由32个连续线程组成，在一个warp中所有线程按SIMT方式执行：所有线程执行相同的指令，每个线程在私有数据上进行操作

从硬件角度看不再有高维的grid和block概念，所有线程都被组织成一维的warp.当一个线程块中有128个线程的时候，其分配到SM上执行时，会分成4个warp：

warp0: thread 0,……..thread31

warp1: thread 32,……..thread63

warp2: thread 64,……..thread95

warp3: thread 96,……..thread127

对于二维或三维block的唯一线程id可以计算

threadIdx.y * blockDim.x + threadIdx.x

threadIdx.z * blockDim.y * blockDim.x + threadIdx.y * blockDim.x + threadIdx.x

block内的warp数量 = [block总线程数/warp大小]_向上取整

如果block总线程数量不是warp线程数量的偶数倍，那么最后的一个线程束内有些线程就不会活跃。如下图总共80个线程(2x40)被划分为3个warp，用96个硬件线程去支持80个软件线程，最后半个warp是不活跃的，即使并未被使用但他们仍然消耗SM的资源比如寄存器。

warp分化#

GPU支持传统C风格显示的控制流结构，比如if、else、else if、for、while。

CPU拥有复杂度的硬件来执行分支预测，在每个条件检查中预测程序的控制流会使用哪个分支，如果预测正确CPU中的分支只需要付出很小的性能代价。如果预测不正确CPU可能会停止运行很多周期，因为指令流水线被清空。

GPU没有复杂的分支预测机制，一个warp中的所有线程在同一周期中必须执行相同指令，如果一个线程执行一条指令，那么warp中的所有线程都必须执行该指令。当函数中存在控制流分支时，warp中的不同线程需要执行不同分支时这样的操作肯定会产生问题。在同一个wra中的线程执行不同指令被称为warp分化。

如果warp中的线程产生分化，warp将连续执行每一个分支路径，禁用不执行这一路径的线程 。

每个线程都执行所有的if和else部分，当一部分cond成立的时候，执行if块内的代码，有一部分线程cond不成立那就等待，等大家都完成，再进行下一轮（也就是下一个指令）

分化会导致性能显著下降，分支条件越多并行性削弱越严重。注意分化只会放生在同一warp中，不同warp不同的条件不会引起warp分化。

举一个分化计算例子，使用threadIdx % 2作为条件，紫色是等待，可以看到下图中同一时间内 一半的线程在等待，一半的线程在执行if或else

在编程中尽量避免同一warp中存在不同的执行路径，同时注意block中的warp分配是固定的，每32个线程是一个warp，可以以此划分不同warp统一执行不同分支。在编程中使用warp方法来交叉存取数据而非使用线程方法，以此避免warp分化。

比如上面这个例子可以使用 (threadidx / warpSize) % 2作为条件，使执行分支的粒度是warp大小的倍数来避免warp分化，每个warp执行固定的那个分支。使用下述代码来测试两种条件带来的性能差异，代码中warmup部分是提前启动一次GPU，因为第一次启动GPU时会比第二次速度慢一些

资源分配#

warp的上下文资源包含，程序计数器、寄存器、共享内存。warp的上下文在其声明周期中是保存在芯片内的，所有从一个上下文切换到另一个上下文没有损失(大概一两个时钟周期)。每个SM都有32位寄存器组，存储在寄存器文件中，并可以在线程中进行分配，同时SM的共享内存也会被分配给block。

SM中来自于同个内核函数的block和warp数量，受限于SM中内核所需的寄存器和共享内存大小。下图展示的就是若每个线程消耗的寄存器数量越少，一个SM终中的warp数量越多。

资源会限制SM中常驻block的数量，每个SM的寄存器和共享内存数量受计算能力限制，如果每个SM都没有足够的共享内存或寄存器去处理至少一个块，那么内核将无法启动。

当寄存器或共享内存被分配给block时，block被称为活跃的block，他所包含的warp被称为活跃的warp，其可被进一步细分为下面3种 选定的warp、阻塞的warp、符合条件的warp

SM上的warp调度器在每个时钟周期都选择活跃的warp，将其调度到指令执行单元。活跃的被执行的warp被称为选定的warp，如果一个活跃的warp准备执行但尚未被调度执行则被成为一个符合条件的warp，如果一个warp没有做好执行准备，则它是一个被阻塞的warp。

是否符合条件，由下面的因素决定：32个CUDA core可被用于执、当前指令中的所有参数都已准备就绪

对于Kepler SM上的活跃warp数量必须<= 64(架构限制)，任何时钟周期中，选定的warp数量都<=4。如果warp阻塞，warp调度器会找一个符合条件的warp替代它。因为资源在在warp中分配的，而且warp的整个声明周期都在片上，所以warp调度 上下文切换非常快。为了最大化利用GPU，需要让大量warp保持活跃。

延迟隐藏#

GPU利用率与常驻warp数量直接相关。从指令发出到指令完成的时钟周期被定义为指令延迟。当每个时钟周期，每个SM的warp调度器都能找到一个符合条件的warp时，可达到计算资源的完全利用。指令延迟的隐藏可以简单理解为不让SM有空载的机会，当某个指令在执行时有源源不断的符合条件的warp指令在被添加等待调度(期望用warp的延迟可以被其他warp的执行隐藏，提高数据吞吐量)，此时SM满载利用率拉满

指令可基本分为两种： 算术指令和内存指令，算术指令延迟是指一个算术操作从开始到它产生输出之间的时间。内存指令延迟指发送的加载或存储操作到数据到达目的地之间的时间。 一般算术指令延迟为10-20个时钟周期，全局内存访问延迟为400-800个时钟周期。

下图我warp 0阻塞执行流水线的一个例子，当warp 0阻塞调度器会选取其他warp执行，直到warp 0符合条件。

估算隐藏延迟所需的活跃warp数量，利用little law计算 所需活跃warp数量 = 延迟 x 吞吐量(throughput)

比如内核的一条指令平均延迟是5个周期，为了保持在每个周期执行6个warp的吞吐量，则至少需要30个未完成的活跃warp

带宽和吞吐量经常被混淆，可看CUDA1.5 HPC基本概念，带宽通常指理论峰值 单位时间内最大可传输的数据量，吞吐量指已达到的值 单位时间内完成的指令数量。

下图列出了32位浮点a+b x c算术运算所需要的总并行操作数量 (隐藏算术延迟所需要的操作数量 延迟 * 吞吐)，吞吐量由SM中每个周期执行的操作数量确定，一个warp一个时钟周期执行32个操作(一个warp 32个线程)，所以对于Fermi而言每个SM中需要保持20(640/32)个warp。

通过上面的计算可知，可通过两种方法提高并行：

指令级并行ILP:一个线程中有很多独立指令，这些指令可并行执行

线程级并行TLP:并发大量符合条件的线程

对于内存操作来说，其所需的并行可表示为每个周期内隐藏内存延迟所需的字节数。吞吐量通常表达为每秒千兆字节数。需要先用内存频率将吞吐量转换为每周时钟期千兆字节数。

内存读取的延迟隐藏是为了使用全部的内存带宽(计算指令的延迟隐藏是为了利用全的计算资源(活跃的warp数量))，内存延迟的时候，计算资源正在被别的线程束使用，所以我们不考虑内存读取延迟的时候计算资源在做了什么。

可通过下面的命令检测设备内存频率

nvidia-smi -a -q -d CLOCK | fgrep -A 3 “Max Clocks” | fgrep “Memory”

以fermi为例其吞吐量为144 GB/s，Tesla内存频率为1.566GHz，转为 144GB/s / 1.566GHz = 92字节/时钟周期

内存指令延迟周期数(800) * 吞吐字节/周期(92) = 74KB 单次内存延迟期间的吞吐字节数

特别说明这里的内存带宽是指GPU设备的而非单个SM的。Fermi 需要并行地在内存延迟期间读取74kb的数据才能让GPU带宽满载，隐藏内存延迟。

假设每个线程将4字节浮点从全局内存移动到SM中，在Fermi中需要 74kb / 4 = 18500个线程 ， 18500/32 = 579个warp来实现隐藏所有内存延迟。

Fermi有16个SM，579/16=36个warp/SM 来实现隐藏所有内存延迟。

与计算指令延迟很像，通过在每个线程/warp中创建更多的独立内存指令，或创建更多并发的活跃线程/线程束来增加可用的并行。延迟的隐藏取决于活动的线程束的数量，数量越多，隐藏的越好，但是线程束的数量又受到上面的说的资源影响。所以这里就需要寻找最优的执行配置来达到最优的延迟隐藏。

确定一个线程束的下界呢，使得当高于这个数字时SM的延迟能充分的隐藏，其实这个公式很简单，也很好理解，就是SM的计算核心数乘以单条指令的延迟，比如Fermi的SM有32个单精度浮点计算流水线路，一个计算指令延迟20个时钟周期，那么我需要最少 32x20 =640 个线程/SM 使设备处于忙碌状态，这是一个下界。

为了提高占用率还需要调整block配置，以允许更多的活跃warp提高计算资源利用率，但是极端的block会限制资源利用

小block: block中线程太少，会在所有资源被充分利用前导致硬件到达每个SM的warp限制数量 — 因为block上线程会被分到warp上执行，一个warp至少32个线程 如果block上线程少于32或接近32 会导致warp上存在空闲线程，线程数量小block但多block，会导致出现大量的warp上空闲线程，导致在计算资源被充分利用前，SM的可利用warp数量到顶。

大block: block中线程太多，会导致每个SM中每个线程可用的硬件资源较少( 寄存器和共享资源确实被平均分到的较少 寄存器溢出（Register Spilling）：若线程所需寄存器超过分配值，多余数据会被迫存储到全局内存（Global Memory）或本地内存（Local Memory）。

由于访问全局内存的延迟比寄存器高100倍以上，导致计算单元等待数据，SM利用率骤降。

共享内存由SM内所有Block共享（如Tesla M6为96KB/SM）。大Block会占用更多共享内存，限制SM内可并行的Block数量。

Block并发数降低：例如，若一个Block独占48KB共享内存，则SM最多运行2个Block（而非32个），导致线程槽位空闲。

数据复用效率下降：共享内存常用于减少全局内存访问，资源不足迫使频繁访问高延迟全局内存，计算吞吐量降低

每个SM常驻的线程数有上限（如2048线程/SM）。大Block导致单个Block线程数过多，但SM可运行的Block数量受限于硬件（如H100最多32个Block/SM）。

Warp数量不足：例如，Block线程数为1024时，一个Block包含32个Warp（1024/32）。若SM仅运行1个Block，则仅32个Warp活跃，远低于满配64个Warp。

延迟隐藏失效：Warp调度器依赖多Warp切换隐藏内存延迟。Warp数量不足时，SM计算单元因等待数据而空闲

关于grid和block大小有一些常用的准则，保持每个block中线程数量是warp大小(如32)的倍数，避免block太小每个block至少有128或256个线程根据线程对device资源的需求调整block大小，block的数量要远远多余SM数量，从而保证SM上的常驻block一直占满，真正的最佳配置需要实验调整获得

同步#

barrier synchronization(栅栏同步)是一个原语(原子操作)，在CUDA中同步分两个级别

系统级:等待host和device完成所有工作

对于host来说，许多CUDA API调用和所有的核函数启动不是同步的，cudaDevicesSynchronize函数可以用来阻塞host程序，指导所有CUDA操作(mem copy、核函数)完成

这个函数可能会异步CUDA操作返回错误

block级:device执行过程中等待一个block中的所有thread到达同一点

因为一个block中warp以未定义顺序执行，CUDA提供了一个使用块局部栅栏(block local barrier)来同步它们的执行功能，使用__syncthreads在内核中标记同步点

__device__ void __syncthreads(void);

__syncthreads被调用时，同个block中每个线程都必须等到其他线程也达到这个同步点。在这个栅栏后之前所有线程产生的所有全局内存和共享内存访问修改，将对所有其他线程可见。

同个block中的线程可以通过共享内存和次存起来共享数据，当线程之间共享数据时要避免内存竞争！在其他并发框架中pthread中的锁，openmp中的同步机制来避免内存竞争(多个线程无序访问相同内存，写前没加锁，在写时/写前访问到，如果程序依赖于更新数据那将导致问题，未定义读是在写前还是写后执行，以及写竞争 一个写了另一个覆盖写)。在上面的warp介绍中提到了，物理上并非所有线程在同一时间执行，如果同一block A需要访问B在不同warp中的写结果，只需调用__syncthreads经过块同步后就可以进行读操作，不同步就会出现上述内存竞争。为了避免覆盖写竞争，需要在shared mem中为每个线程结果提前申请空间，预定结果的内存位置防止写覆盖

为什么CUDA不做块和块之间的同步，感觉也是底层设计了块调度方便执行大规模并行

__syncthreads只能同步同一个块内的线程，不能同步不同块内的线程，想要同步不同块内的线程，就只能让核函数执行完成，控制程序交换主机，这种方式来同步所有线程。

可扩展性#

可扩展性其实是相对于不同硬件的，当某个程序在一个SM上执行的时候时间消耗是T当我们使用两个SM时，其资源是设备1的两倍，我们希望得到T/2的运行速度，这种性质是CUDA驱动部分提供的特性，目前来说 Nvidia正在致力于这方面的优化(在c++中使用多线程加速，耗时降低的倍数一定是小于实际线程数的，这是因为线程的同步资源分配等等有额外开销，Nvidia的开发经可能降低SM间同步和切换的开销)

在可变数量的计算核心上执行相同的代码能力被称为透明可扩展性。CUDA内核启动时grid中的block以并行或连续或任意顺序被执行，block被分到多个SM中。block就是一个基础的独立计算单位，这种独立性使得CUDA程序在任意数量的计算核心间可扩展。

并行归约问题(Parallel Reduction)#

对N个元素的数组求和，串行代码如下。

int sum = 0;
for(size_t i = 0;i < N;++i)
    sum += array[i];

如何通过并行计算来加速这个求和，加法存在结合率和交换律，数组元素可以以任何顺序求和，可以用以下方法执行并行加法运算。

1 划分数组 2 用一个线程计算一个block中的部分和 3 对每个block的部分和再求和得到最终结果

常用的实现方法是，一个block值包含一对元素，并且一个线程对这两个元素求和产生局部结果，将局部结果inplace保存在输入的数组中，这些值被作为下一次迭代求和的输入，因为经过一次迭代后需要计算的元素减半，当需要计算的元素长度为1是最终结果就已经被计算出来了。有点像递归求完全二叉树叶子节点的和的过程，计算左右叶子节点的和，将和赋给跟节点返回上层递归，如此迭代直到返回根节点(相邻配对，其过程如下图是颗倒着的完全二叉树，递归的最深层只有一个元素是上面所谓"根节点")。

根据求和后结果的存储位置，可以将实现进一步分为相邻配对(元素直接与它们相邻的元素配对)

int recursiveReduce(int *data, int const size)
{
	// terminate check
	if (size == 1)
        return data[0];
	// renew the stride
	int const stride = size / 2;
	if (size % 2 == 1)
	{
		for (int i = 0; i < stride; i++)
		{
			data[i] += data[i + stride];
		}
		data[0] += data[size - 1];
	}
	else
	{
		for (int i = 0; i < stride; i++)
		{
			data[i] += data[i + stride];
		}
	}
	// call
	return recursiveReduce(data, stride);
}

任何满足交换律和结合律的运算都可以用类似的方法实现，比如求max、min、平均、乘积

blockIdx.x*blockDim.x为block对应子数组的起始索引，blockDim.x为子数组的大小。0号线程参与3次计算，2，6线程参与1次计算，4号线程参与2次计算。如上图每层就是单个for stride的计算过程

__global__ void reduceNeighbored(int * g_idata,int * g_odata,unsigned int n)
{
    //set thread ID
    unsigned int tid = threadIdx.x;
    //boundary check
    if (tid >= n) return;
    //convert global data pointer to the
    int *idata = g_idata + blockIdx.x*blockDim.x; // 此block对应子数组的起始索引，blockDim.x为子数组的大小
    //in-place reduction in global memory
    // stride可以理解为层，第一层就是和相邻元素相加,第二层(0,2),(4,6)相加计算...
    // 可以看到只有偶数线程参与计算(偶数索引元素inplace修改)，奇数线程陪跑(奇数索引元素不变) warp发生分化!
    for (int stride = 1; stride < blockDim.x; stride *= 2)
        {
            if ((tid % (2 * stride)) == 0)
            {
                idata[tid] += idata[tid + stride];// 直接inplace在input上修改
            }
            //synchronize within block
            __syncthreads();// 当前层元素修改后同步
        }
    //write result for this block to global mem
    if (tid == 0)
        g_odata[blockIdx.x] = idata[0];// 将次block的部分和保存，由于block间无法同步需要copy到host再进行串行的block间求和

}

在每次归约循环结束后，stride *= 2，在第一次循环结束后idata的偶索引元素被部分和替换，第二次循环结束后idata 索引%4==0 元素被新的部分和替换…

有一点，需要注意实际任务中数组不可能每次都是2的整数幂，如果不是2的整数幂需要确定数组边界。

循环展开#

通过减少分支出现的频率和循环维护指令来优化循环。循环展开中，通过重复多次循环主体代码 从而减少总的循环次数，通过重复循环主体代码减少迭代次数或完全删除循环，循环体的赋值数量被称为循环展开因子，迭代次数就变为原始总迭代次数/循环展开因子，当提前知道总迭代次数，通过循环展开是非常有效的优化方法

简单解释一下为啥for while和if,switch同属分支语句

循环展开是一个尝试通过减少分支出现的频率和循环维护指令来优化循环的技术。循环展开通过减少指令消耗和增加更多的独立调度指令来提高性能，更多的并发操作被加入流水线以产生更高的指令和内存带宽。为warp调度提供更多符合条件的warp来帮助隐藏指令或内存延迟

	int *idata = g_idata + blockIdx.x*blockDim.x*2;
	if(idx+blockDim.x<n)
	{
		g_idata[idx]+=g_idata[idx+blockDim.x];

	}
	__syncthreads();
	//in-place reduction in global memory
	for (int stride = blockDim.x/2; stride>0 ; stride >>=1)
	{
		if (tid <stride)
		{

		}

		__syncthreads();
	}
	//write result for this block to global mem
	if (tid == 0)
		g_odata[blockIdx.x] = idata[0];

}

展开线程的归约#

__syncthreads用于block内的线程同步，用于确保线程在经过同步后，已经将局部结果全部写入全局/共享内存中了。同个wrap内的执行是SIMT(单指令多线程)，可以将求和归约写为如下形式而非循环+线程同步

**volatile关键字告诉编译器和硬件，不要对这个指针指向的内存进行激进的优化（比如将值缓存到寄存器中）。它确保每次对vmem[tid]的读写操作(写要求必须将vmem值存会全局内存)都直接发生在内存（这里是全局内存）**上，并且保证写入操作对其他线程立即可见。

带volatile修饰的全局或共享内存，编译器会假定其值可以被其他线程在任意时间修改或使用，因此任何volatile修饰的变量强制读或写全局/共享内存，而不是简单地读写缓存或寄存器。

动态并行#

上面说的核函数都是从host端被调用的，gpu的工作完全被cpu控制。cuda的动态并行允许在GPU端直接创建和同步新的cuda核，在一个核函数中的任意点动态增加并行的GPU程序，主要用在递归算法上使得代码更清晰，其运行效率没有提高，动态并行，相当于串行编程的中的递归调用，递归调用如果能转换成迭代循环，一般为了效率的时候是要转换成循环的，只有当效率不是那么重要，而更注重代码的简洁性的时候，我们才会使用

有了动态并行以后可以在运行时决定需要在GPU上创建多少grid和block，可以动态利用gpu调度器和加载平衡器

在gpu端创建任务的能力可以减少在主机和设备之间传输执行和数据的需求

嵌套执行#

在动态并行中，由于是在核函数中新启动一个核函数，所以需要对正在被调用的核函数做区分。分为父grid/block/thread和子grid/block/thread。子grid父thread启动，且必须在对应的父thread，父block，父block结束之前结束。所有的子grid结束后，父thread，父线block，父grid才会结束。

主机启动一个内核-> 此grid（父grid）在执行的过程中由父thread启动新的grid（子grid）->所有子grid都运行结束后-> 父grid才能结束，否则要等待

图中显式的同步了父grid和子grid，通过设置栅栏的方法(某些sync方法)

父grid中的不同thread启动的不同子grid，这些子grid拥有相同的父block，他们之间是可以同步的(通过sync同步，block共享内存)

gpu并行动态中天然存在隐式同步:如果父block中的所有线程在子grid完成前退出，那么子grid隐式同步会被触发。隐式同步就是虽然没用同步指令，但是父block中虽然所有线程都执行完毕，但是依旧要等待对应的所有子grid执行完毕，然后才能退出

cpu隐式同步需要调用对应的函数：前面我们讲过隐式同步，比如cudaMemcpy就能起到隐式同步的作用，但是主机内启动的内核，如果没有显式同步，也没有隐式同步指令，那么cpu线程很有可能就真的退出了，而你的gpu内核可能还在运行

父block启动子grid需要显示的同步，也就是说不同的父wrap需要都执行到子grid调用那一句，这个block内的所有子grid才能依据所在线程束的执行，执行一次

关于内存:

父grid和子grid共享相同的全局和常量内存。

父grid子grid有不同的局部内存

有了子grid和父grid间的弱一致性作为保证，父grid和子grid可以对全局内存并发存取

有两个时刻父gird和子grid所见内存一致：子grid启动的时候，子grid结束的时候

共享内存和局部内存分别对于block和thread来说是私有的

局部内存对线程私有，对外不可见.比如在父thread上的局部内存指针传到子grid核中是无效的
