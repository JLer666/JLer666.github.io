3 malloc/free malloc源码太复杂，稍微讲下运作模式， 一次要1M(不够再继续要) 一个header管理1M(sbh初始会拿16个header 16个不够用则后续申请更多)，1个header管理32Group,1个Gruop管理32k(由virtual_malloc向OS commit地申请内存，即这32k一定得到)1个Gruop管理64条链表，分为8个page(1页4k)。这么复杂的管理，就是为了分段细分管理小内存，能够将分出去的小内存重写收回来变为大的连续的内存，从而才能够还给OS,如果1块就1M不再进行细分，1M分出去切成小块再完整的全部会后回来的时间一定比32k(系统真正在做的是在管理1段32k–1个group的内存)切成小块分配出去再完整地回收回来的时间要长，当我们把管理的最小单位划的够小，那么我们完整地回收回这一连续的最小单位内存的概率越大。 Group除了64条链表的指针外还有一个cnt计数器只要malloc就++只要free就–，所以只要cnt==0时就意味着malloc分出去的内存都收回链表了，此块group 32k是连续完整的。当一个group全回收了，会将一个header_defer指针指向这个group所属的header,一个groupdefer索引记录这个group是哪个group,当再有第二个全回收group出现sbh将会释放第一个全回收group,而如果没有出现第二个全回收group而又从这个已全回收的group中取出block完成分配，此时这个group又不是全回收状态了，则将会把header_defer指针置为Null。malloc cookie int记录的就是此块连续内存的大小 程序**要求内存(malloc)**在1024byte(其实是1016)之内,vc调用 __sbh_alloc_block 函数分配heap,否则调用windows系统自带的 HeapAlloc 函数 分配内存 图1的heap_init函数 分配了 16 个 Header用来管理SBH 图1的ioinit 函数调用malloc_dbg要了程序的第一片内存,在debug模式下是256个byte,为了要到这一块内存,他会调用接下来的一系列函数 图1的heap_alloc_dbg 为所有的内存块分配debug块并且在内存块上下放4byte的’无人区’,用来在debug模式下进行调试,防止使用者超出内存块 图一的 heap_alloc_base 判断分配的内存是否在1016+2*cookie(4byte)之内,来决定要不要调用 sbh_alloc_block sbh_alloc_block把每个block(包括debug头和无人区)调成16的倍数,但是cookie显示为16的倍数再加一个标志(检查是否被分配给应用程序) heap_init 分配的每一个 Header 管理 1M的虚拟内存,通过new 一个region来管理,region通过 图一的 sbh_alloc_new_region 来分配,每一个region里面还有32个group 和 64bit->其中存放内存管理的信息 最后,windows 32k(一段) 32k地给 程序物理内存 一个group 管理 32个 32 k 32个group 每一个都是一个内存池(64条双向链表,64个池) 回收内存 用户调用free,free调用 SBH 回收内存把 cookie 的最后一位改为0,然后把指针拉到group的一个链表内就行 内存合并 内存必须得合并,不然回收的内存会越来越碎片化,系统会越来越恶劣 合并内存通过观察将要回收的内存块的上下内存块的cookie最后一位是否为0,如果为0,就可合并当前内存块和上下内存块的cookie,这样就合并完成,再挂载到group(哪一个group?,哪一个Header?)的相应链表 哪一个Header&group: 由于知道Header的头指针和Header的长度(1M), 看p在不在某一Header的头指针到尾部之间,就可确定Header。同理可获得对应的group编号(指针-Header头/32k)，这样分段(1M->32k->4k)管理是为了更好地归还内存给OS。

1 VC6 malloc() 之前讲过VC6 malloc后得到的一块内存的实际布局 其中block size是我们申请的大小(图中我们申请的是ch 十六进制 对应12字节)，上下cookie占用8个字节，当我们申请的内存比较小 cookie的在这块内存(比如我们申请的12字节)的占比比较大，这造成了较大的浪费，所以在std::allocator中对于申请较大的内存直接调用malloc,而对于较小的内存为了减少cookie带来的浪费用的就是我们之前讲的先申请一大块内存专门用于某个 大小较小的对象 的内存分配(大内存 分为sizeof(对象)大小 的节点 并用指针将这些节点首位相连变为一条链表)。 我们工程中遇到较多的是 需要海量的小区块这种情况，对象的占用大小不大，但是需要申请大量的对象。 此时大量对象造成的cookie浪费是无法忍受的，所以就需要allocator对大小较小的对象进行内存管理。 2 标准分配器实现 std::allocator 不同编译器对于分配器的实现都有所不同 vc6 的allocator只是直接使用全局版本的 ::operator new，::operator delete (背后就是 malloc和free)来完成allocate()和deallocate() 并没有什么改进。所有内存块都是带着cookie BC5标准分配器也是直接使用全局版本的 ::operator new，::operator delete (背后就是 malloc和free)来完成allocate()和deallocate() 并没有什么改进。所有内存块都是带着cookie(去除cookie的前提区块的大小都一样大即同种数据类型放在一起，但如果一块内存为不同类别分配内存，需要cookie记录每个分配出去的空间大小) G2.9(Gnu 2.9)也是直接使用全局版本的 ::operator new，::operator delete (背后就是 malloc和free)来完成allocate()和deallocate() 并没有什么改进。 这个allocator的头文件中有这样的注释 此头文件并没有被include到任何的容器类中，此文件仅仅是为了与老版本兼容。 G2.9的所有容器使用的分配器不叫std::allocator而是叫std::alloc, template<class T,class Alloc=alloc> class vector{....}; void* p = alloc::allocate(512);//alloc是个类 allocate，deallocate是其中的静态函数才可以这样不通过对象来直接调用 alloc::deallocate(p,512); 下面是2.9的alloc 在较新的Gnu编译器版本中 比如GNU4.9 std::alloc叫做__gnu_cxx::__pool_alloc(体制外非std分配器)，其实跟2.9版没有区别 就是变量名称换了 就是我们之前写的链表的形式 ...

4 new handler(new中出现错误的异常处理) 当op new无法分配出你所申请的memory,会抛出一个异常std::bad_alloc exception。 某些老的编译器则是不抛出异常返回0，我们现在也可以通过new(nothrow) Foo来实现不抛出异常。 如果抛出异常，在抛出异常之前会先(不止一次) p==0只要malloc返回0，就循环调用_callnewh(size),_callnewh(VC下叫这个)就是我们的new_handler,在_callnewh调用完后 异常不一定会被抛出(前提是我们的new_handler起作用了 出现了一些空余空间)，再次循环 调用一个由客户(我们)定义的handler,一下是new handler的形式和设定方法 typedef void(*new_handler)();//函数指针 指向new异常处理函数 //返回值为void 无参数的函数 new_handler set_new_handler(new_handler p) throw(); //set_new_handler的函数原型 我们登记函数p 函数将会把上级的处理函数指针返回给我们 new_handler是为了让更多的内存可用，在无内存的时候看看哪些不重要的内存先释放。我们也可以在new_handler中调用abort()或exit() 举个例子 set_new_handler原型 #include <new> void noMoreMemory() { cerr << "out of memory"; abort(); //若没有abort 会不断输出out of memory" //因为全局默认的op new就是在不断地循环调用new_handler //直到获得足够的内存 } void main() { set_new_handler(noMoreMemory); int *p = new int[100000000000]; //故意申请超大内存 引起new_handler assert(p); } 5 =default,=delete(c++ 11新增关键字) class Foo{ public: //=default 表示这个函数要用默认版本 //有默认版本的函数=default只适用于 拷贝构造函数 拷贝赋值函数= 析构函数 //=delete 表示不要这个函数 //=delete也适用于 new/new[] delete/delete[] Foo()=default; Foo(const Foo&)=delete; Foo& operator=(const Foo&)=delete; ~Foo()=default; ..... };
