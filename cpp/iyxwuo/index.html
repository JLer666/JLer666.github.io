5 gnu4.9下的bitmap allocator

bit map allocatot有个特点 当allocate或deallocate的元素个数为1个时(n==1),会调用专门的allocate or deallocate _single_object，当allocate或deallocate的元素个数大于1个调用的是全局的::op new or delete

super block = super block size + use count +bitmap + blocks

block 容器要的一个元素(对象)大小的空间 图中的一个小格

一次性拿64个blocks(未来两倍成长 这个大小增长是指数级的增长极快),一个block区块的大小规定为8的整数倍大小

super block size = bitmap+blocks+use count(一个计数变量) 的大小，但是不包含自己这个记录size大小的变量本身的大小

(灰色表示blocks中的第一个block分出去了 则bitmap[0]的第一位设置为0)初始是64个区块 所以需要64个bit(位) 记录每个区块是否被分出去了，这64个bit(位)就是两个bit map(1个32位 unsingned int)–1表示在手中，0表示这个block分出去了

用了63个余下最后一个的情况

use count 用于计数分出去了多少个block

使用一个__mini_vector(并不是标准库vector容器，而是写了一个小型的vector,因为分配器本身就是为容器服务的，但是分配器本身又用到容器 不太好 这个问题之前讨论过)来管理多个 super block(__mini_vector的一个节点为一个super block)—

__mini_vector除了节点首地址外(相当于数组首地址)有3个成员变量，_M_start,_M_finish分别指向第一个vector节点的首地址和当前正在工作的最后一个vector节点的末尾地址。_M_end_of_storage指向vector最后一个节点(可能并没在工作–并没有让这个节点管理super block)的末尾地址(__mini_vector的容量是2倍成长的，所以__mini_vector可能有节点–superblock并没有用到 是申请出的余量 _M_end_of_storag指针就是指向所有vector节点的最后)，__mini_vector的一个节点 (entry)图中蓝色的两个方块 保存super blocks中的第一个和最后一个block的首地址。

分配

当第一个super block(64 blocks)的block用光了(vector中的第一节点(一开始只有一个节点)都没有block可用了)。会申请第二个super block(vector 节点)，第二个super block中block的数量就是第一个super block的两倍为64*2=128个。128个bit所以需要4个32字节的bitmap，注意不止super block中block的个数会两倍成长，vector的growed up每次也会增长为原来两倍的节点数(growed up会引起内存的搬移 比如这张图中的第一个节点的地址在growed up为两个节点后已经发生了移动–注意是节点的地址蓝色小块的开头会变，其中管理的block的地址是不变的)

当第2个super block用光(vector中的两个节点都没有block可用了)，将会grow up申请vector节点–原来是2个节点现在grow up后变为4个节点，即要多出两个节点。为第3个节点申请super block,super block中blocks的数量也两倍成长变为128*2=256个block，第4个节点不申请super block 待用(如果申请super block其对应的block数量为256–只有在vector grow up后才会将super block对应的block数量成倍增长)。

每一个entry(一个vector节点–一个super block)代表一种value type(对象类型)，一个super block不会为 不同的value type(对象类型)即使大小相同(对象的大小相同)提供block

回收

当第一个super block(64个block的那个)全回收，使用了另一个与min vector类似的结构叫free list,free list的一个节点(节点中含1个指针成员)指向了这个super block(目前free list管理这个super block未来会将它释放)，min_vector断开与这个super block的连接(调用的是erase 被erase节点右边的节点全部向左边推一位，erase的那个节点变为min vector中的最后一个待用节点)，min_vector对应的节点变为空闲，并且下次super block中block数量减半将变为128(如果没回收下次 min vector节点的super block应该含256个block数量)。

free list中最多管理64个全回收min vector节点，当出现65个便将free list中管理的最后一个交还给OS

free list 管理规则

free list中接管的super block的顺序是根据super block的大小(其中block的数量)来排列，super block(成员变量super block size)小的排在list的前端。当free list要接管第65个super block，检查这最新一个的大小 如果大于list中最末尾(最大)的super block则直接将这个新进者交给OS释放，否则先将当前list最末尾的super block交给OS释放，再按大小关系插入到list中适当的位置。
